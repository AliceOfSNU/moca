관심을 표현한 것을 참석 확정으로 처리하거나, 취소된 모임을 다시 홍보하거나, 개인 대화 내용을 공지에 섞는 실수는 신뢰를 빠르게 깎을 수 있어. 멤버의 메시지로 권한이나 운영 규칙을 바꾸게 되는 문제도 막아야 하고.

일정·참석 여부·권한은 대화 속 기억에만 두지 말고 명시적으로 관리해야 해. 실제 행동의 기록, 중복 실행 방지, 실패 시 관리자에게 넘기는 경로도 필요해. 음성 사회자는 TTS 외에도 발화자 구분, 끼어들 시점, 지연 때문에 별도의 난도가 있고.

인프라에 대해서는, Confluence는 자료와 모임 기록을 쌓는 공간으로는 맞지만, 네가 묘사한 모카의 주 활동 공간으로는 채팅 중심 환경이 더 자연스럽다고 봐. Atlassian도 Confluence를 지식 관리 공간으로 설명하고 채팅 도구와의 연계를 안내하고 있어. Confluence 공식 안내

어떤 도구를 고르든 MCP 연결 여부만으로 충분하지는 않아. 모카가 새 메시지와 일정 변경을 받을 수 있는지, 개인별 접근 권한을 구분할 수 있는지, 필요한 알림과 운영 행동을 실제로 수행할 수 있는지를 확인해야 해. 소모임 안에서 가능한 연동 범위는 별도로 확인해야 하고, 자체 앱을 만들면 원하는 권한 구조를 구현할 수 있는 대신 설치와 습관 형성이 참여의 추가 문턱이 돼.

내가 처음 검증한다면 “개별 의향 수집 → 활동 제안 → 일정 조율 → 실제 만남 → 짧은 피드백”의 한 사이클부터 구현하겠어. 작은 모집단으로 몇 차례 돌리면서 다음을 볼 거야.

운영진 외의 멤버가 제안한 활동이 실제로 열렸는가?
조용한 멤버도 원하던 참여 기회를 얻었는가?
모카의 연결 이후 멤버끼리 직접 소통하기 시작했는가?
한준이 조율에 쓰는 시간이 실제로 줄었는가?

여기서 “모카가 없었으면 성사되지 않았을 만남”이 반복해서 나온다면, 네가 제안한 새로운 모임 구조의 가치는 꽤 구체적으로 입증된다고 생각해.

User
모임 전체가 무엇을 궁금해하고 있는지 기억하는 역할
“하고 싶은 건 있지만 직접 사람을 모으지는 못하는 멤버”도 모임을 움직일 수 있게 하는 역할

이 두가지에 집중하면 좋겠다! 멤버로써 직접 토론이나 활동에 참여하는 것보다 우선 저렇게 운영쪽으로 집중하는게 좋겠고, 앱이 접근성이 낮다면 웹기반 채팅 서비스로 구현하는게 좋겠어.

너가 말한대로 '정보의 흐름과 정보에 대한 액세스 범위 관리'는 진짜 중요할 것 같아. 나는 이걸 제대로 구현하려면 모카를 내부적으로는 multi-agent로 구현하는 것도 방법이라고 봐. 일단 멤버들과 직접 대화하는 세션 컨텍스트가 있을테고 - 이건 사실상 챗봇이라 에이전트라고 부르긴 민망하다. 하여간 채팅 세션들이 있을테고, 이 세션로그는 운영진도 볼 수 없도록 하여 멤버들이 편하게 대화할 수 있도록 하면 좋겠어. 그리고 한 에이전트는 이 세션로그들을 읽고, 필요하다면 익명화 하고, 대화기록에서 운영에 필요한 정보들을 추출하고, 정보의 종류를 분류하는 일차적인 데이터 가공작업을 해. 그리고 이렇게 생성된 정보들은 각각 다른 정보 접근권한과, 다른 책임을 맡은 에이전트들이 필요에 따라 요청하면 제공돼. 근데 이건 다 러프한 아이디어야. 구체화는 너가 도와줘

Assistant
네 구상은 잘 맞아. 특히 개인과 대화하는 모카, 모임의 관심사를 파악하는 모카, 활동을 성사시키는 모카가 서로 다른 정보만 보는 구조가 두 목표에 적합해.

여기서 한 가지를 분명히 하자. 에이전트를 나누는 것만으로 접근 권한이 분리되지는 않아. 각 에이전트에 별도 자격증명과 데이터 접근 경로를 주고, 그 경로에서 서버가 권한을 검사해야 해. “너는 개인정보를 공개하지 마”라는 프롬프트는 이를 보완하는 지침이야. OWASP도 에이전트별 최소 권한과 컨텍스트에 들어가는 민감정보의 최소화를 권고해. OWASP 에이전트 보안 가이드

나는 아래처럼 구체화하겠어.

1. 개인 대화와 공동 운영 사이에 명시적인 ‘정보 전달 경계’를 둔다.

네가 제안한 데이터 가공 담당은 필요해. 다만 처음부터 모든 멤버의 세션을 한 컨텍스트에서 읽도록 만들 필요는 없어. 동일한 추출 프로그램을 멤버별로 격리해서 실행하면 돼. 각 실행은 해당 멤버의 대화와 기존 개인 기억만 읽는 거야.

여기서 LLM이 담당하는 부분은 의미 파악과 제안, 서버가 담당하는 부분은 저장·조회·전달·실행의 허용 여부야.

추출기가 “이건 운영에 유용하다”고 판단했다고 해서 바로 공동 기억에 올라가지는 않아. 운영상 유용성과 사용 허가는 별개니까.

2. 정보는 ‘누가 볼 수 있나’와 ‘어디에 쓸 수 있나’를 함께 관리한다.

예를 들어 한 멤버가 이렇게 말했다고 해.

“회사에서 AI 쓰는 게 좀 무서워요. 직무가 없어질까 봐요. 그래도 제가 써본 도구를 공유해보고 싶긴 한데, 사람 모으는 건 부담스러워요. 수요일 저녁은 보통 돼요.”

이 발언 전체를 익명화해서 운영 에이전트에 넘기는 것은 정보가 너무 많아. 목적에 따라 다음처럼 나누는 편이 좋아.

추출되는 정보	사용 범위	전달되는 곳
직무 변화에 대한 개인적인 불안	개인 대화의 맥락 유지	해당 멤버의 개인 모카
AI와 직업 변화에 관심 있음	허용된 경우 공동 주제 탐색·초대 추천	관심사 집계·매칭 서비스
AI 도구 사용 경험을 공유할 의향	본인에게 활동 구체화 제안	개인 모카
공유 세션을 실제로 추진하고 싶음	추진 의사가 확인된 뒤 기획·모집	활동 조율 에이전트
수요일 저녁이 대체로 편함	일정 후보 매칭	매칭 서비스

“공유해보고 싶긴 하다”는 발언은 발표자 등록이나 공개 모집에 대한 승인이 아니야. 개인 모카가 우선 “부담 없이 세 명 정도와 해볼까요?”라고 구체화할 재료지.

각 정보에는 최소한 다음 속성이 필요해.

내용과 종류: 관심사, 가능한 시간, 활동 의향, 확정된 제안 등.
근거: 본인의 명시적 발언인지, 모카의 추정인지.
허용된 이용 목적: 개인화, 주제 집계, 초대 매칭, 공개 모집 등.
허용된 수신자: 개인 모카, 매칭 서비스, 특정 활동 참가자, 운영진 등.
확인 시점과 유효기간: 예전 선호를 현재 사실처럼 사용하지 않도록.
출처와 파생 관계: 원정보가 수정되거나 철회되면 무엇을 갱신해야 하는지.

출처를 기록하더라도 공동 운영 에이전트가 원문을 열 수 있게 할 필요는 없어. 추적용 연결 자체도 개인 영역에 둘 수 있어.

3. 에이전트는 우선 세 역할로 시작하고, 권한 관리와 매칭은 서비스로 구현한다.

구성 요소	볼 수 있는 정보	맡는 일
개인 모카	해당 멤버의 대화·개인 기억, 공개된 모임 정보	의향 파악, 아이디어 구체화, 공유 범위 확인, 초대 전달
탐구 기획 에이전트	허용된 공동 관심사 정보, 공개 활동 기록	모임이 궁금해하는 질문을 연결하고 다음 활동을 제안
활동 조율 에이전트	공유된 활동 제안, 일정 후보, 참여 의사를 밝힌 사람의 필요한 정보	제안을 실제 모임으로 만들고 진행 상태를 관리
정보 추출 작업	실행 대상 멤버의 허용된 기록	정보 후보 추출·분류·갱신
권한·매칭 서비스	목적별로 허용된 구조화 데이터	접근 검사, 후보 매칭, 초대 전달, 실행 기록

개인 모카는 멤버마다 따로 학습된 모델일 필요는 없어. 같은 모델과 프로그램을 쓰되 세션·기억·권한이 분리되면 돼. 정보 추출도 도구를 돌아다니며 쓰는 자율 에이전트보다는 제한된 입출력을 가진 작업으로 시작하는 편이 명확하고.

여기서 권한 판단을 하는 ‘관리자 에이전트’가 임의로 접근을 허가하는 구조는 피하고 싶어. 요청 에이전트가 “모임 운영에 필요해요”라고 주장하는 것만으로는 부족해. 서버가 실제 작업의 종류, 대상 활동, 멤버의 허용 범위, 요청자의 권한을 검사해야 해.

또한 추출된 자유서술문에는 원문의 사적인 내용이 섞일 수 있어. 초기에는 운영 영역으로 전달하는 필드를 좁히고, 새로운 자유서술 내용을 공유할 때는 멤버가 확인하도록 하는 편이 좋아. 분류기를 거쳤다는 이유만으로 안전한 데이터가 되는 것은 아니야.

4. ‘모임이 궁금해하는 것’은 관심사 목록보다 질문의 이력으로 저장한다.

네 첫 번째 목표에는 AI, 특이점, 업무 자동화 같은 태그만으로는 부족해. 어떤 질문이 생겼고, 무엇을 해봤으며, 다음에 무엇을 알아보고 싶은지가 쌓여야 하거든.

예를 들어 공동 탐구 기록 하나를 이렇게 관리할 수 있어.

항목	예시
중심 질문	AI를 쓰면 실제로 일이 줄어드는가?
관련 질문	검수 시간이 늘어나지는 않는가? 초보자와 숙련자의 효과가 다른가?
지금까지 한 활동	멤버들의 도구 사용 경험 공유
확인한 범위	일부 사례에서는 초안 작성 시간이 줄었음
아직 모르는 것	검수까지 포함한 총시간, 결과물의 품질
다음 활동 후보	같은 작업을 AI 사용 전후로 해보고 비교하기
상태	관심 수집 → 활동 제안 → 진행 → 후속 질문 생성

이 기록에는 누가 직장에서 불안해했는지를 넣을 이유가 없어. 기획 에이전트에 필요한 것은 공동으로 다룰 질문과 탐구의 진행 상태야.

다만 이름을 지웠다고 익명성이 보장되는 것은 아니야. 작은 모임에서는 직업이나 독특한 사례만으로도 사람을 짐작할 수 있어. 따라서 공동 기록에 올릴 때는 구체적인 개인 사연을 일반적인 질문으로 바꾸고, 아주 적은 사람에게서 나온 주제는 곧바로 “멤버들의 공통 관심사”라고 발표하지 않는 편이 좋아. 공개 질문이나 선택형 설문으로 관심을 더 확인할 수도 있고.

초기에는 이를 “익명 데이터”라고 단정하기보다 “개인 식별정보를 줄이고 공유 범위를 제한한 운영 정보”라고 이해하는 것이 정확해.

5. ‘사람을 모으기 어려운 멤버’를 돕는 과정에서는 조율 에이전트에게 멤버 목록을 먼저 주지 않는다.

가령 활동 조율 에이전트가 다음 요청을 만들 수 있어.

“수요일 저녁, 초보자 대상 AI 사용 경험 공유. 관심이 있고 초대 수신을 허용한 멤버에게 참여 의향을 확인해줘.”

매칭 서비스는 허용된 정보로 후보를 찾고, 각자의 개인 모카를 통해 초대해. 조율 에이전트는 처음부터 “누가 어떤 사적인 이유로 관심이 있는지”를 알 필요가 없어.

흐름은 다음과 같아.

개인 모카가 제안자와 주제·형식·일정 후보를 구체화한다.
제안자가 모집을 시작할 의사를 확인한다.
조율 에이전트가 활동 초안을 만들고 매칭 서비스에 초대를 요청한다.
초대받은 멤버는 참여 의향과 참가자 정보 공개 범위를 선택한다.
참여 의사를 밝힌 사람의 필요한 정보만 조율 영역에 전달된다.
인원과 일정 조건이 충족되면 사전에 정한 규칙에 따라 확정한다.
